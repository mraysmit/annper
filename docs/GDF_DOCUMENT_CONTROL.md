## 1. Authority and precedence

The controlled set is exactly four documents. Every other artifact is either
generated from them or lives outside the document set.

| Precedence | Artifact | Authority |
|---:|---|---|
| 1 | `GDFramework Functional Specification.md` | Normative observable behavior, functional scope, compatibility contract, non-functional requirements (section 44), and the legacy defect disposition register (section 31) |
| 2 | `GDF_MODERN_WEB_SYSTEM_DESIGN.md` | Normative logical design, design-verification requirements (`WDES-*`), and implementation boundaries for the modern web equivalent |
| 3 | `GDF_MIGRATION_MASTER.md` | Governance, delivery sequence, decision register, risks, quality gates, reference baseline and evidence boundary (sections 23–24), component/dependency/API/dataset/provider inventories (sections 25–29), and architecture decision records (section 30) |
| 4 | `GDF_DOCUMENT_CONTROL.md` (this document) | Approval, versioning, precedence, change history, and the generated requirement traceability matrix (section 8) |

An approved ADR in `GDF_MIGRATION_MASTER.md` section 30 governs one technical
decision within the boundaries of the documents above it. Superseded drafts are
not retained in the working tree; they remain in git history (the 0.1 design
and plan drafts were last present at commit `bb1991a`).

A target-design, ADR, or migration-plan statement may not silently override a
functional requirement. A deliberate behavior change requires:

1. an approved `Preserve`, `Fix`, or `Retire` decision recorded in the
   functional specification section 31 register;
2. the affected requirement and test rows regenerated in section 8;
3. an ADR when architecture or compatibility is affected; and
4. a new controlled document version.

A verified desktop-bound behavior that cannot be carried into the browser
unchanged is not a defect. It is listed in functional specification section
32.1, and its web reinterpretation is approved under decision D-017 at Gate B, before implementation of the
dependent workflow (FR-INV-012).

## 2. Status vocabulary

| Status | Meaning |
|---|---|
| Working | Actively edited and not suitable as a gate baseline |
| Controlled working baseline | Versioned and internally checked; external evidence or approval remains outstanding |
| Approved baseline | Named approvers accepted the defined scope and evidence |
| Superseded | Replaced by a named later version; retained only in git history |

“Controlled” does not mean an authored application is fully specified. The
functional specification's completeness boundary remains binding.

## 4. Portable evidence-root convention

`LEGACY_SOURCE_ROOT` means the root of the read-only legacy GDFramework tree.
All functional-specification paths are resolved from
`${LEGACY_SOURCE_ROOT}/Docs` because they were originally recorded relative to
that folder. The sibling GUI tree is `${LEGACY_SOURCE_ROOT}/../GenData/AppGUI`.

The tools under `tools/` take the root only from that environment variable or
an explicit parameter; they embed no share or machine path. When the root is
unreachable, `Build-ControlledArtifacts.ps1` reuses the committed checksum
baseline and `Test-Documentation.ps1` reports the source-path checks as
skipped. The reviewed instance on 6 September 2026 was a network share
identified in `GDF_MIGRATION_MASTER.md` section 23; that is evidence about the
reviewed copy, not a required path.

## 5. Version and change rules

- Patch version: clarification or evidence-link repair with no behavior change.
- Minor version: added/changed requirements, dispositions, architecture, or gate
  logic.
- Major version: approved scope or compatibility baseline changes materially.
- Every version records its date, summary, and approval state in section 6;
  the owner is the register owner in section 3, the approvers are the roles
  named in section 7 for that artifact, and the legacy checksum-manifest
  identity is recorded in each document header.
- Section 8 is a reproducible output of `tools/Build-ControlledArtifacts.ps1`.
  It embeds no timestamp, so an unchanged input set regenerates byte-identical.
  Edit the source documents or the generator, never the generated rows.
- Defect decisions are recorded in the functional specification section 31
  table (`Decision`, `Approvers`, `Approval date` columns) so regeneration never
  discards an approved disposition.
